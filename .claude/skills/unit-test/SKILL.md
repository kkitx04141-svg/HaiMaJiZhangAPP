# 单元测试技能

为"黑马记账"项目编写、执行单元测试，并给出测试报告。

## 测试框架

本项目使用 **Vitest** 作为测试框架，已配置好：

- **配置文件**：`vitest.config.ts`（项目根目录）
- **测试文件位置**：和源码放在一起，命名为 `xxx.test.ts` 或 `xxx.test.tsx`
- **运行命令**：`npx vitest run`（一次性运行）/ `npx vitest`（监听模式）
- **路径别名**：测试中可以用 `@/` 开头来导入 renderer 目录下的模块，如 `@/utils/formatMoney`

## 工作流程

收到用户指令后，按以下步骤执行：

### 第一步：确定测试范围

分析用户意图，判断要测试什么：

1. **用户明确指定了文件/函数** → 只测指定的内容
2. **用户说"测所有"或没有指定范围** → 按优先级来：
   - 优先测试 `src/renderer/utils/` 下的纯函数（金额格式化、日期格式化等）
   - 其次测试 `src/renderer/db/` 下的数据操作函数
   - 再次测试 React Hooks（`src/renderer/hooks/`）
   - 最后才是 React 组件

用简洁的语言向用户确认测试范围，然后继续。

### 第二步：阅读源码

在写测试之前，必须先仔细阅读要测试的源文件，搞清楚：

- 每个函数的输入参数是什么、返回值是什么
- 有哪些边界情况和异常情况需要覆盖
- 函数有没有副作用（如操作 DOM、读写数据库）

### 第三步：编写测试文件

遵循以下规范来写测试：

**（1）文件位置**：测试文件放在被测试文件的同一目录下。
```
例：src/renderer/utils/formatMoney.ts
   → src/renderer/utils/formatMoney.test.ts
```

**（2）文件结构**：
```typescript
/**
 * [模块名] — 单元测试
 */
import { describe, it, expect } from 'vitest'
import { 被测试的函数 } from '@/路径/模块名'

describe('函数名 — 一句话描述', () => {
  it('正常情况 — 具体描述', () => {
    expect(函数调用).toBe(期望值)
  })

  it('边界情况 — 具体描述', () => {
    expect(函数调用).toBe(期望值)
  })

  it('异常情况 — 具体描述', () => {
    expect(函数调用).toBe(期望值)
  })
})
```

**（3）测试用例要覆盖**：
- ✅ 正常情况（happy path）：最常见的输入
- ✅ 边界情况（edge case）：0、空字符串、最大/最小值
- ✅ 异常情况：负数、非法输入等

**（4）命名规范**：
- `describe` 用函数名 + 一句话概述（中文）
- `it` 用具体场景描述（中文），格式："什么情况 → 预期结果"

**（5）禁止事项**：
- ❌ 不要测试第三方库的功能（如 React 本身的行为）
- ❌ 不要写需要真实 Electron 环境的测试
- ❌ 不要修改被测源码来"凑"测试通过

### 第四步：运行测试

用以下命令执行测试：

```bash
npx vitest run
```

这个命令会：
- 找到所有 `.test.ts` 和 `.test.tsx` 文件
- 执行所有测试用例
- 输出详细的通过/失败结果

### 第五步：给出测试报告

测试跑完后，用中文向用户汇报，格式如下：

```
## 🧪 单元测试报告

| 项目 | 数值 |
|------|------|
| 测试文件数 | X 个 |
| 测试用例数 | X 个 |
| ✅ 通过 | X 个 |
| ❌ 失败 | X 个 |
| ⏱️ 耗时 | X.XX 秒 |

### 通过的测试（示例）
- ✅ 正常情况 — 正整数分转元（2550 → "25.50"）
- ✅ 边界情况 — 零分转元
- ...

### 失败的测试（如有）
- ❌ 某测试名称
  - 期望：xxx
  - 实际：xxx
  - 可能原因：xxx
```

如果全部通过，最后加一句肯定的话（如"所有测试全部通过 ✅"）。
如果有失败，分析失败原因，给出修复建议，并询问用户是否需要修复。

## 注意事项

1. **只测纯逻辑**：本项目是 Electron 应用，数据库依赖主进程 IPC。工具函数可以直接测，涉及 IPC/数据库的代码需要考虑 mock。
2. **先跑后说**：写完后先自己跑一遍确认能通过，再向用户报告。
3. **不要过度测试**：不会有人因为你写了 100 个测试而感谢你。关注核心逻辑和容易出错的函数。
4. **如果测试失败**：仔细阅读错误信息，判断是测试写错了还是源码有 bug。如果是源码 bug，明确告诉用户。
